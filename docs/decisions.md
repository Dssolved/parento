# Принятые решения и их причины

Здесь зафиксированы неочевидные технические и продуктовые решения — чтобы новая сессия не
переделала их «по-нормальному», не зная контекста. Формат: решение → почему → что будет, если менять.

Дата среза: 2026-09-02.

---

## D1. UUID курсов из исходного ТЗ — выдуманные, миграция переписана под реальные

**Решение.** `supabase/add-adaptive-weeks.sql` проставляет диапазоны недель курсам с ID вида
`00000000-0000-4000-8000-0000000001XX`, а не тем UUID, что были в ТЗ.

**Почему.** В ТЗ на персонализацию был готовый блок `update courses set week_from = ... where id =
'b8d1072b-...'` для 13 курсов. В базе таких ID нет: реальные демо-курсы из `demo-content.sql`
используют паттерн `00000000-0000-4000-8000-...`. Первая версия миграции была написана по ТЗ и
отработала «успешно», не обновив **ни одной строки** — из-за этого у всех курсов остались
`week_from = null`, а `isRelevantForWeek` считал такие курсы актуальными всегда. Внешне это выглядело
как «персонализация показывает вообще всё подряд».

**Если менять.** Любые UUID вида `b8d1072b-...`, `6b7ad3af-...` и т.п. из старого ТЗ — мусор.
Перед написанием UPDATE по ID всегда сверяться с `demo-content.sql` или с базой.

## D2. «Актуально сейчас» показывает только курсы с явно заданным диапазоном недель

**Решение.** Есть две функции проверки: мягкая `isRelevantForWeek` (курс без диапазона актуален
всегда) и строгая `isTimelyForWeek` (диапазон обязателен). Секцию «Актуально сейчас» питает
**строгая**. «Якорные» курсы (сквозные, на весь путь) сознательно оставлены с `week_from = null`.

**Почему.** По ТЗ null-диапазон означал «актуален всегда», и формально такие курсы попадали
в «Актуально сейчас». Но секция, которая обещает «важное именно на вашей неделе», а показывает
курс про всю беременность целиком, обесценивает саму фичу. Разделение получилось чистое: узко
привязанные курсы → в секцию персонализации, сквозные → живут в общем каталоге ниже.

**Если менять.** Переключение секции на `isRelevantForWeek` вернёт в неё все курсы без диапазона —
то есть эффект «показывает всё подряд», от которого мы уходили. `isRelevantForWeek` оставлена
в коде осознанно, для мест, где нужна мягкая семантика.

## D3. Рекомендации сортируются от узкого окна к широкому

**Решение.** `useRecommendedCourses` сортирует по ширине диапазона `week_to - week_from`.

**Почему.** Чем уже окно, тем точнее курс «про сейчас». Курс на недели 14–27 полезнее на 20-й неделе,
чем курс на недели 6–36, хотя формально подходят оба.

## D4. Фильтр и сортировка по неделям работают только внутри одного этапа

**Решение.** Блок фильтра «Неделя» в каталоге появляется только при выбранном конкретном этапе
`pregnancy` или `newborn`. Режим «Актуально для меня» дополнительно требует совпадения выбранного
этапа с этапом профиля и сравнивает неделю только с курсами того же этапа.

**Почему.** Недели у этапов измеряют разное: 20-я неделя беременности и 20 недель жизни малыша —
несравнимые величины. Без ограничения пользователь на 20-й неделе беременности получил бы в
«актуальном» курс для малыша с диапазоном 0–24, потому что число просто попало в интервал.
При этапе `all` или `planning` фильтр скрывается, а смена этапа сбрасывает выбранный режим,
чтобы не остался невидимый активный фильтр.

**Если менять.** Любое расширение фильтра на «Все этапы» обязано учитывать `course.stage`,
иначе вернётся ложное срабатывание.

## D5. Кастомный `DatePicker` в формах, но слайдер — в демо-виджете

**Решение.** Для ввода ПДР и даты рождения написан свой компонент
`src/components/ui/DatePicker.tsx` вместо нативного `<input type="date">`. А в демо-виджете на
лендинге — не календарь, а слайдер недели.

**Почему.** Нативный date input выглядит по-разному в браузерах и на выборе «13 января» легко
промахнуться годом (для ПДР это критично — год почти всегда следующий). Свой календарь показывает
месяц и год явно, ограничивает диапазон (`min`/`max`) и говорит по-русски.
В демо на лендинге задача обратная — не аккуратно ввести дату, а мгновенно увидеть эффект: слайдер
даёт отклик на каждое движение, календарь требовал бы лишних кликов и убивал бы «вау».

## D6. Продуктовые события пишутся в Supabase, а не в Vercel Custom Events

**Решение.** Сначала события были сделаны через `track()` из `@vercel/analytics`, затем перенесены
в собственную таблицу `events` (Supabase). Компонент `<Analytics />` для pageviews оставлен.

**Почему.** Custom Events в Vercel Web Analytics доступны только на Pro (плюс отдельный add-on
Web Analytics Plus). На бесплатном Hobby вызовы `track()` уходят, но в панели их не видно вообще —
то есть данные собирались бы в никуда. Для MVP, где аналитика событий это отдельная зона
ответственности в команде и основа для решений pivot/persevere, невидимые данные бесполезны.
Своя таблица: бесплатно, данные принадлежат проекту, смотреть — обычным SQL.
Pageviews при этом на Hobby работают штатно и бесплатно, их переносить незачем.

**Если менять.** Возврат на Vercel-события имеет смысл только вместе с оплатой Pro.
Ссылки: [лимиты Web Analytics](https://vercel.com/docs/analytics/limits-and-pricing),
[custom events](https://vercel.com/docs/analytics/custom-events).

## D7. Трекинг клика по карточке курса — только в секциях персонализации

**Решение.** `CourseCard` принимает необязательный проп `analyticsSource`. Событие
`recommended_course_clicked` отправляется только если проп передан — а он передаётся лишь в
«Актуально сейчас» (`catalog_recommended`, `dashboard_recommended`).

**Почему.** Метрика должна отвечать на конкретный вопрос: даёт ли персонализация клики. Если трекать
все карточки одинаково, вопрос размывается. Общий каталог намеренно не трекается.

**Если менять.** Добавляя трекинг общего каталога, вводите отдельный `source`, а не расширяйте
существующий — иначе исторические данные в `v_recommended_course_clicks` станут несравнимыми.

## D8. Истечение пробного Premium — ленивое, без cron

**Решение.** При активации Premium в `profiles.premium_expires_at` пишется `now() + 7 дней`.
Откат на `free` делает `AuthContext.fetchProfile`: при очередной загрузке профиля, если срок прошёл,
подписка обновляется в БД и локально.

**Почему.** Альтернативы — Vercel Cron или Supabase Edge Function — тянут инфраструктуру и
(в случае cron на Vercel) платный тариф, при том что инфраструктурные расходы проекта сейчас ≈ 0.
Ленивая проверка не требует ничего и происходит ровно тогда, когда результат нужен. Главный
выигрыш: **все существующие проверки доступа не изменились** — `access.ts`, `CourseCard`, `Navbar`,
страницы курса и урока по-прежнему читают просто `profile.subscription`, ничего не зная про сроки.

**Компромисс, принятый сознательно.** Пока пользователь не открывает приложение, в базе он числится
Premium сверх срока. Для продукта без оплаты это неважно; при подключении платежей проверку сроков
надо будет переносить на сервер (и закрывать RLS, см. риск в current-state §4.1).

## D9. Демо-виджет на лендинге не обращается к базе, карточки некликабельны

**Решение.** `WeekDemo.tsx` держит захардкоженный массив демо-курсов, повторяющий диапазоны из
`add-adaptive-weeks.sql`. Карточки — не ссылки.

**Почему.** Виджет стоит на главной странице и обязан работать всегда. Живые данные дали бы два
способа опозориться: пустая секция, если миграция не накатана или диапазоны не совпали с текущей
датой, и мёртвый блок при недоступной БД. Плюс лендинг публичный, а таблицы курсов читаются под
анонимным ключом — лишняя зависимость ради витрины не нужна.
Некликабельность — потому что у демо-карточек нет реальных ID: ссылка вела бы на 404.

**Цена решения.** Массив надо синхронизировать вручную, если реальные диапазоны курсов изменятся.

## D10. Один общий хелпер склонений вместо локальных функций

**Решение.** `src/lib/pluralize.ts` с формами `[один, два-четыре, много]`.

**Почему.** Баг «1 уроков» оказался не единичным: та же строка без склонения нашлась в профиле,
на странице курса и в шести местах дашборда, а на странице подписки уже жила своя локальная функция
склонения дней. Один хелпер вместо девяти строковых литералов и двух копий одной логики.

## D11. Лендинг не обещает того, чего в продукте нет

**Решение.** С лендинга убрана карточка «Экспертное сообщество». В формулировках сознательно не
используются «единственная платформа» и «экспертная поддержка».

**Почему.** Сообщества в продукте нет, и по бизнес-плану оно осознанно не строится на старте
(UGC — это источник того самого шума, с которым Parento борется). «Единственная платформа» —
непроверяемое превосходство, которое легко разбить одним контрпримером. «Экспертная поддержка»
подразумевает живых консультантов, которых пока нет. Обещания, которые продукт не выполняет,
бьют по доверию — а доверие здесь основной актив.

**Если менять.** Возвращать эти формулировки можно только вместе с самой функциональностью.

## D12. Мажорные апгрейды зависимостей отложены

**Решение.** В `b586ec8` обновлены только патч/минорные версии. Отложены: `tailwindcss` 3→4,
`react-router-dom` 6→7, `vite` 6→8 вместе с `@vitejs/plugin-react` 4→6, `typescript` 5→7,
`@types/node` 20→26.

**Почему.** Tailwind 4 — новый движок и другой формат конфига, задевает каждый файл с классами.
React Router 7 — breaking changes в роутинге (в консоли уже висят предупреждения про флаги
`v7_startTransition` / `v7_relativeSplatPath`). Vite и его react-плагин надо двигать вместе.
TypeScript «7» — это не инкремент, а переход на новый нативный компилятор (переписан на Go)
со своей нумерацией, слишком свежий. `@types/node` — только типы, апгрейд бессмысленен без
перехода на новый Node в рантайме.

**Как делать.** По одному, отдельными коммитами, с прогоном `tsc`/`lint`/`build` и ручной проверкой.

## D13. `.claude/launch.json` не коммитится

**Решение.** Файл есть локально, в git не добавлен.

**Почему.** Это конфиг превью-сервера для ассистента с портом 5199 — порт выбран, чтобы не
конфликтовать с дев-сервером пользователя на 5173. В репозитории он только сбивал бы с толку.

## D14. `schema.sql` оставлен базовым, изменения живут в миграциях

**Решение.** `supabase/schema.sql` не переписывается под текущее состояние БД; все изменения —
отдельные `add-*.sql`.

**Почему.** Так видно историю и понятно, что применять на существующей базе. Обратная сторона:
для новой БД нужен `schema.sql` **плюс** все миграции по порядку — это описано в
[supabase-migrations.md](./supabase-migrations.md).

**Если менять.** Схлопывание в один актуальный `schema.sql` допустимо, но тогда надо явно
пометить старые миграции как исторические, иначе непонятно, что накатывать на живую базу.
